# Начальные справочники Midnight Steep

Скрипты для PostgreSQL и текущей схемы API. Сначала применить миграции проекта,
включая `20261103090000_SimplifyGameSchema` (убирает лишние поля прогресса,
рецептов и мебели, поворот и дублирующий слой расстановки).

## Запуск

В pgAdmin выбрать базу игры, открыть **Query Tool**, загрузить и выполнить **весь**
`01_reference_data.sql`. Затем при необходимости выполнить `02_furniture_catalog.sql`.
В каждом файле есть собственная транзакция и итоговая выборка.
Если pgAdmin сообщил об ошибке внутри транзакции, выполнить `ROLLBACK;` перед повтором.

Альтернатива из PowerShell в каталоге API (указать свои имя базы и пользователя;
пароль psql запросит сам):

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h localhost -U postgres -d MidnightSteep -v ON_ERROR_STOP=1 -f .\Scripts\Seed\01_reference_data.sql
& 'C:\Program Files\PostgreSQL\18\bin\psql.exe' -h localhost -U postgres -d MidnightSteep -v ON_ERROR_STOP=1 -f .\Scripts\Seed\02_furniture_catalog.sql
```

## Данные

Основной скрипт добавляет 5 уровней, 2 персонажа, 8 ингредиентов, 10 напитков
и 26 строк состава рецептов. Одна строка `Recipes` — один ингредиент напитка;
на порцию всегда нужна одна единица каждого указанного ингредиента.
`cooking_time` — секунды.

| Уровень | Всего заказов | Нужно выполнить | Выручка | Новые напитки |
| --- | ---: | ---: | ---: | --- |
| 1 | 5 | 3 | 60 | Чёрный чай, сладкий чай |
| 2 | 8 | 5 | 100 | Чай с молоком, чай с лимоном |
| 3 | 12 | 8 | 160 | Медовый чай с лимоном, ягодный чай |
| 4 | 16 | 11 | 220 | Лавандовый чай, розовый чай |
| 5 | 20 | 15 | 300 | Ночной цветочный чай, полуночный ягодный чай |

`Characters.id = 1` — мальчик, `id = 2` — девочка: именно такие значения передают
кнопки текущей сцены Unity. При конфликте этих ID с существующими персонажами
скрипт остановится, чтобы не переименовать персонажей чужих сохранений.

Дополнительный скрипт добавляет 23 товара: мебель, декор, пол, обои и 8 ящиков
ингредиентов. Базовые покрытия, прилавок, печь и ящики бесплатны: новый игрок
начинает с нулём монет, и покупка источников ингредиентов не должна блокировать
первый заказ. Ящики открываются вместе с напитками, использующими их содержимое.
Цены и пороги — стартовый баланс для прототипа, их можно менять в `VALUES`.

## Повторный запуск и связи

Уровни сопоставляются по `level_number`, ингредиенты, напитки и товары — по
`asset_name`. Существующие ID сохраняются, недостающие строки добавляются,
поля справочников обновляются, недостающие связи рецептов добавляются. Повторный
запуск не создаёт дубликаты. Другие строки не удаляются, включая дополнительные
ингредиенты уже существующих рецептов. Неоднозначные `asset_name` вызывают ошибку.
Последовательности ID учитывают уже вставленные вручную значения.

`unlock_level_id` и `unlocked_level_id` получают **ID строки уровня**, найденного
по номеру: ID уровня не обязан совпадать с номером. По текущей логике API напитки
и товары открываются, когда соответствующий уровень доступен.

`Users`, `Saveses`, `Inventories`, `PlacedItems`, `LevelProgresses` — данные игроков,
они не заполняются этими скриптами. API создания сохранения сам открывает первый
уровень; последующие уровни открываются при прохождении предыдущих.
Стартовый набор выдаётся автоматически при первом `POST /save`, после выбора
персонажа: по одному `PinkLamp`, `Table`, `RedChair`, `HoneyKettle`,
`CrateTeaLeaves` и `BarCounter` (шесть экземпляров). Инвентарь связан с сохранением,
поэтому сама регистрация аккаунта ещё не создаёт предметы. Повторный вход и
повторное создание сохранения не начисляют набор. Существующие сохранения
не изменяются. Другие товары приобретаются через магазин API.

При успешном прохождении уровня `POST /levels/complete` открывает следующий
уровень и автоматически добавляет по одному ящику новых ингредиентов его рецептов.
Учитываются все рецепты открываемого уровня; один ингредиент даёт один ящик.
Ингредиенты, используемые хотя бы в одном уже доступном рецепте (включая напитки
с `unlock_level_id <= 0`), повторно не выдаются. Уже принадлежащий игроку ящик
не дублируется. При повторном прохождении, непрохождении или отсутствии следующего
уровня ящики не начисляются. По текущим справочникам после уровня 1 выдаются
молоко и лимон, после 2 — мёд и ягоды, после 3 — лаванда и лепестки розы;
после 4 и 5 новых ингредиентов нет. Сахар уже используется в рецептах первого
уровня и не входит в заданный стартовый набор.

Ящик награды сопоставляется с ингредиентом по точному `asset_name`
(`crate_milk`, `crate_lemon` и т. д.). Нужен каталог `02_furniture_catalog.sql`.
Если ящик отсутствует или его ключ неоднозначен, завершение отклоняется без
записи прогресса и начислений. Открытие уровня, выдача и монеты записываются
одной транзакцией с блокировкой сохранения, включая одновременные запросы.
В текущем Unity-клиенте отправка результата смены в `/levels/complete` ещё не
подключена: выдача выполняется сервером при вызове этого метода. Открытие
инвентаря заново загружает начисленные предметы через существующий GET.

Перед созданием новых сохранений выполнить `04_starter_furniture.sql`.
Скрипт добавляет недостающие строки каталога по точным ключам Unity, сохраняет
существующие ID, цены и характеристики, не меняет данные игроков. Повторный
запуск безопасен. Если в каталоге отсутствует предмет набора или ключ неоднозначен,
API отклоняет создание сохранения целиком. Успешное создание записывает сохранение,
первый уровень и весь стартовый инвентарь в одной транзакции.

`HoneyKettle` — плита с чайником. В `Teahouse.unity` префаб подключён в магазине
и инвентаре, как и ящики с ключами `crate_*`. Полка для сладостей использует
`TeaShelf` и не входит в стартовый набор; барная стойка — `BarCounter`.

## Ассеты и ограничения текущей схемы

Ключи товаров и ингредиентов совпадают с именами существующих PNG в Unity:
`Assets/Images/UI/InventoryShop-v1/Thumbnails/`. Для ингредиентов используются
изображения соответствующих ящиков. `asset_name` — ключ для сопоставления на
клиенте; эти файлы не находятся в `Resources`, поэтому сам SQL не подключает спрайты.

Ключи напитков `drink_*` — новые логические имена: отдельных изображений этих
напитков пока нет. Можно сопоставить все ключи с имеющимся `tea_cup.png`.
`Furnitures.placement_layer` использует `Floor`, `Wall`, `Table`; Unity-префабы
должны поддерживать соответствующие поверхности. В `PlacedItems` слой не
дублируется: API возвращает его в `item.placement_layer` из справочника мебели.
Размещение декора на мебели хранится через `parent_placed_item_id`.

В текущей БД нет связи «ящик мебели → ингредиент» и таблицы запасов ингредиентов.
Ящики представляют многоразовые источники; расходуемость определяет игра.
Общий `asset_name` позволяет сопоставить ящик и ингредиент, но не создаёт FK
и сам по себе не реализует выдачу или расход ингредиентов. Модель учёта запасов
и игровая логика приготовления потребуют отдельной реализации.

## Проверка

`05_room_coverings.sql` добавляет DarkWoodFloor и LightBueWallpaper бесплатно
с первой смены для проверки смены покрытий. Повторный запуск не создаёт
дубликатов и не меняет существующие товары или сохранения игроков.
Команда валидатора `seed-coverings` сначала сохраняет JSON каталога в `.backups`,
затем выполняет этот скрипт в рабочей БД.

При проверке использовать изолированную схему PostgreSQL: первичное заполнение,
повторный запуск без дубликатов и внешние ключи рецептов. Рабочие сохранения
не должны заполняться или перезаписываться начальными справочниками.


## Настольные лампы

`07_desk_lamp_variants.sql` добавляет `BlueDeskLamp` и `WhiteDeskLamp` по характеристикам существующей `DeskLamp`: цена, комфорт, лимит и доступность наследуются при добавлении. Предметы появляются в магазине, после покупки — в инвентаре; размещаются на столах. Повторный запуск не дублирует строки и не меняет существующие настройки.

## Полный каталог Unity и стандартные предметы

`06_complete_furniture.sql` добавляет восемь тёмных полок с ингредиентами и две мусорки, сохраняя существующие цены и ID. Для существующих сохранений выдаёт отсутствующие `HoneyTrashBin`, `BlueWallpaper`, `WoodFloor` по одному экземпляру. Повторный запуск не увеличивает уже имеющееся количество. Перед выполнением на рабочей БД рекомендуется резервная копия.

Новые сохранения получают эти три предмета вместе с прежними шестью: всего девять типов. Базовые обои и пол выбираются по `asset_name`, без фиксированных ID. Для чистой БД сначала выполните `04_starter_furniture.sql`, затем `06_complete_furniture.sql`.
